# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Siam Wheels Rental Hub (brand: Drive Dee), a Thai-language car rental prototype. TanStack Start + React 19 + Supabase (via Lovable Cloud). `README.md` has the full feature, role and database overview; `AGENTS.md` has the Lovable rules. Read both before non-trivial changes.

## Commands

```sh
npm run dev                               # dev server, http://localhost:8080
npm test                                  # vitest run (all tests, UI + DB)
npx vitest run src/test/payment-window.test.ts   # one test file
npx vitest run -t "name fragment"         # tests by name
npm run lint
npx tsc --noEmit                          # type-check
npm run build
```

- `npm run preview` does not serve the Cloudflare Worker output; use `npm run dev`.
- The checkout uses `core.autocrlf=true`, so on Windows `npm run lint` reports a prettier "Delete `␍`" error on every line. Check real lint problems with `npx eslint --rule "prettier/prettier: off" <files>` and format with `npx prettier --end-of-line auto --write <files>`.
- Under full-suite load a few UI tests (e.g. `admin-invite-flow`) can hit the 5 s timeout; rerun the file alone before treating it as a failure.

## Architecture

- **Routing:** file-based in `src/routes/` (see `src/routes/README.md`). `cars_.$id.tsx` / `bookings_.$id.tsx` use a trailing underscore so the detail page is not nested under the list page. Every page sets its own `head()` title ending in `— Drive Dee`. `routeTree.gen.ts` is generated; do not edit (the dev server rewrites it; do not commit that churn).
- **Business rules live in the database, not the UI.** Booking validation, overlap checks, price, holds, payment and contract transitions are Postgres functions/triggers protected by RLS (`drizzle/migrations/`). Client code in `src/lib/` mirrors these rules for display only; keep the two consistent. If the UI and the DB disagree, the DB wins and the UI shows its (Thai) error message.
- **Contract workflow** (migration `0004`; `0005` made contracts self-service and `0006` rolled it back, so live behaves as 0004): a booking (`pending`, with `hold_expires_at`) gets a contract that moves `draft → pending_customer → … → approved → paid`, with immutable `contract_versions` and an append-only `contract_events` log. Contracts change only through RPCs (`admin_create_contract`, `admin_update_contract`, `admin_send_contract`, `customer_accept_contract`, `customer_request_revision`, `pay_booking`, …); `guard_contract_update()` rejects any other update. `src/lib/contract-workflow.ts` mirrors the allowed transitions (`CONTRACT_TRANSITIONS`, checked against the SQL by `contract-workflow.test.ts`) and derives the customer's stage; `src/lib/contract-api.ts` wraps the RPCs.
- **Booking fee flow** (migration `0007`, source `docs/database/booking-fee-flow.sql`): customer confirms the sent contract → status goes straight to `approved` with a 15-minute payment window → `pay_booking` charges a fixed 1,000 THB fee (`booking_fee()`, mirrored by `BOOKING_FEE` in `src/lib/booking-fee.ts`). Deposit = rent. After the fee the customer pays the rest online with `pay_pickup` (`docs/database/pickup-payment.sql`, pending in Lovable) (rent + deposit − fee; `payments.kind = 'pickup'`, `payments.deposit` = the refundable part, which `src/lib/reports.ts` excludes from revenue). The deposit refund at return is display only.
- **Roles and admin permissions:** `admin` / `customer` in `user_roles`, resolved by `src/hooks/use-auth` and `src/lib/roles`. Admins additionally have per-permission grants in `admin_members` (`contracts_manage`, `contracts_approve`, `bookings_manage`, `fleet_manage`, `reviews_moderate`); one Owner invites/suspends admins via `/admin-invite`. `/demo-admin` exists but its `demo_admin` role is not in the database yet.
- **Supabase clients** are in `src/integrations/supabase/` (generated; `types.ts` is regenerated by Lovable). The service-role key is used only by the `createDemoAccount` server function; never expose it to browser code. An RPC not yet in the generated types needs a cast: `db.rpc("name" as never, args as never)`.
- **Demo mode:** all payments are simulated. Test card `4242 4242 4242 4242` succeeds; any number ending `0002` is declined client-side and never reaches the DB. Demo Customer accounts use the `@demo.siamwheels.invalid` domain and `app_metadata.demo`.
- Money in THB, dates in Asia/Bangkok (`bangkokTime`, `bangkokTimestamp` helpers), UI text in Thai. Branch hours for pickup/return are 08:00–18:00 (`OPENING_TIME` / `CLOSING_TIME`).

## Tests

- UI tests (`src/test/*.test.tsx`) mock `@/integrations/supabase/client` with a table/RPC stub (`mocks.tables`, `mocks.rpc`); assert on the RPC name and args a click sends.
- DB tests (`src/test/db/*.db.test.ts`, `// @vitest-environment node`) boot an in-memory Postgres with PGlite via `src/test/db/harness.ts`: Supabase auth/roles are stubbed, migrations 0000–0004 are applied (`applyLater: true` adds 0005+, the live stack), and `db.as(user).sql(...)` runs as the `authenticated` role so RLS and grants are real. Fixture helpers: `createUser`, `createAdmin`, `createBooking`, `adminCreate`, `send`, `accept`, `pay`, `expireHold`.
- To test a proposed DB change before Lovable applies it, keep the SQL in `docs/database/*.sql` and apply it in the test with `db.exec(readFileSync(...))` (see `booking-fee-flow.db.test.ts`, which applies `pickup-payment.sql` on top of 0007). Give `beforeAll` a 60 s timeout. Updates to `hold_expires_at` outside the workflow functions are silently reverted by `validate_booking`; use `expireHold`.

## Rules for this repo

- Do not add or edit `supabase/migrations/`, `drizzle/`, or any file whose header says it is generated. Schema changes go through Lovable: draft the SQL and the request in `docs/database/`.
- Lovable syncs only the `main` branch. It cannot read files that exist only on a feature branch, so paste the SQL itself into Lovable, and apply DB changes before merging UI that depends on them.
- Do not rewrite pushed git history (no force push, rebase or amend of pushed commits): the repo syncs with Lovable. Keep the connected branch working.
- Keep secrets out of `.env` (only the two public `VITE_SUPABASE_*` values belong there); private values go in `.env.local`.
